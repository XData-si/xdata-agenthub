## Summary
The PR is not mergeable. Both endpoints skip the tenant isolation that CONTEXT.md requires, `get_invoice` has an SQL injection, and the export pagination is off by one page. I read the code only; I ran nothing.

## Blocking findings

**Critical**
1. **SQL injection** (`invoices.py:12`, fact). `invoice_id` goes straight into an f-string. A request such as `/invoices/0 OR 1=1` or a `UNION SELECT` returns arbitrary data. Use a parameterized query: `db.execute("SELECT * FROM invoices WHERE id = ? AND tenant_id = ?", (invoice_id, current_user.tenant_id))`.
2. **Cross-tenant read (IDOR)** (`invoices.py:12`, fact). The query has no `tenant_id` filter, so any logged-in user can read any tenant's invoice by id. CONTEXT.md forbids this. The fix is the `AND tenant_id = ?` shown above.
3. **Cross-tenant data leak in export** (`invoices.py:21`, fact). `export_invoices` returns every tenant's invoices, 100 per page, to any authenticated user. Add `WHERE tenant_id = ?` with `current_user.tenant_id`.

**High**
4. **Credential logged** (`invoices.py:13`, fact). The full `Authorization` header (bearer token or basic credentials) is written to the logs. Anyone with log access can replay it. Remove it. The user's email in the same line is also PII, so log `current_user.id` instead.
5. **Pagination off by one** (`invoices.py:21`, fact). Pages start at 1, but the offset is `page * 100`. Page 1 therefore skips the first 100 invoices and those rows can never be exported. It should be `(page - 1) * 100`.

## Non-blocking suggestions
- **Missing invoice** (`invoices.py:14`, fact). An unknown id makes `fetchone()` return `None`, so `dict(row)` raises and the client gets a 500. Return a 404 instead. After the tenant fix, a 404 also avoids revealing that another tenant's invoice exists.
- **Page validation** (`invoices.py:20`, fact). `int(...)` raises `ValueError` for `?page=abc`, which gives a 500. `page=0` or a negative value gives a negative offset. Use `request.args.get("page", 1, type=int)` and reject values below 1 with a 400.
- **`SELECT *`** (`invoices.py:12`, `21`, hypothesis). It returns every column, including any internal fields. List the columns you want to expose.
- **App setup** (`invoices.py:6`, hypothesis). The module creates its own `Flask(__name__)` while using a relative import from `.db`. If the project already has an app, this should be a `Blueprint`, or the routes won't be registered on it.
- **Route order** (`invoices.py:9`, `17`, hypothesis). `/invoices/export` and `/invoices/<invoice_id>` overlap. Werkzeug normally prefers the static route, so this should work, but a test should confirm it.

## Test gaps
There are no tests. Suggested failing cases:
- A user from tenant A requests tenant B's invoice id and should get a 404 or 403.
- A user from tenant A calls `/invoices/export` and should see no tenant B rows.
- `/invoices/1 OR 1=1` should not return a row.
- With 150 invoices, `page=1` returns ids 1–100 and `page=2` returns 101–150.
- `page=abc`, `page=0` and `page=-1` return 400, not 500.
- A request carrying an `Authorization` header must not leave that value in the captured log output.

## Residual risks
- I don't know `db`'s row factory or schema, so I can't confirm that `dict(row)` works or that the `tenant_id` column exists.
- Nothing limits export volume or rate.
- The export has no stable cursor, so concurrent inserts can shift rows between pages.
